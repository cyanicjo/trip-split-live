## 수행한 점검과 검증 수준

- 공개 사이트의 정적 파일을 확인했다. 당시 배포된 `app.js`가 기준 저장소 코드와 동일했다.
- 별도 PostgreSQL 17.10 테스트 인스턴스를 로컬 주소에만 열었다. Supabase와 같은 `anon`/`authenticated` 역할, pgcrypto, 행 단위 보안과 발행 구성을 사용했다.
- 원본 스키마의 취약한 동작을 재현한 후 실제 변경 스크립트를 적용하고, 기존 행 보존과 재적용 가능성을 비교했다.
- 가짜 여행·이름·은행·계좌·지출만 사용했다. 운영 여행 목록, 실제 계좌 데이터와 공개 문서에 남은 실제 여행은 조회하지 않았다.
- 처음 공개 시작 화면을 열 때 기존 앱 구조에 의해 빈 여행방 하나가 자동 생성됐다. 해당 방에 이름·계좌·지출을 입력하지 않았다. 이후 공격 재현은 로컬 가짜 데이터로 제한했다.
- DB 테스트는 실제 PostgreSQL 권한을 검증한다. 실제 Supabase 게이트웨이·WebSocket 서버·운영 설정을 모두 재현한 것은 아니다. Realtime은 DB 발행 제거와 브라우저 구독 제거를 확인했고, 운영 WebSocket 우회 검증은 하지 않았다.
- 스크립트 삽입 재현은 외부 요청·키 조회 없이 메모리 내 표식만 변경했다. 수정된 실제 앱의 DOM에서 이벤트 속성 및 악성 노드가 생성되지 않는지 확인했다.
- CSV는 생성 결과의 수식 방어를 검증했다. 모든 Excel/Sheets 버전에서 파일을 열어 확인한 것은 아니며, 편집 후 다시 저장하는 과정의 변환은 보장하지 않는다.
- 브라우저의 편집·보기 탭에서 가짜 친구 두 명, 3일 일정, 12,000원 지출을 저장하고, 보기 화면 동기화와 6,000원 정산을 확인했다. 서로 다른 브라우저 제품 전체를 시험한 것은 아니다.
- 기존 정산·일정 테스트와, 실제 앱 함수를 불러오는 신규 보안 테스트를 모두 실행했다. CSV 매핑·미리보기·중복 처리, JSON 내보내기, PDF 출력용 데이터 생성도 검사했다. PDF 파일 렌더러 자체는 이번에 변경하지 않았다.

최신 통합 검증은 DB 보안 58개, 관리자 DB 13개, 프런트엔드 22개(총 93개)와 기존 정산·일정 회귀 테스트가 통과했다. 관리자·CSV 추가 결과는 `ADMIN_CSV_REPORT.ko.md`에 있다. 잠금 파일 기준 의존성 검사에서 알려진 취약점은 0건이었다. 실행 결과는 `TEST_RESULTS.txt`에 첨부했다. 테스트가 운영 적용을 대신하지 않는다.

## 링크와 사용 방식의 변화

1. 신규 보기 ID와 편집 키는 각각 256비트 난수를 사용한다. 보기 ID 자체가 조회 권한이므로 비밀 링크로 취급한다.
2. 편집 링크는 `?trip=…#edit=…` 형식이다. 보기 링크와 내보내기에는 편집 키를 넣지 않는다. 이전 `?edit=…`는 접속 직후 변환하지만, 최초 요청이 서버에 전송된 사실까지 되돌릴 수는 없다.
3. 이전의 짧은 보기 ID는 단독으로 조회할 수 없다. 노출되지 않은 기존 편집 키를 가진 사람은 들어가서 새 보기·편집 링크를 재발급할 수 있다. 재발급은 기존 링크 두 종류를 모두 폐기한다.
4. 공개 기록에서 발견된 키는 위 복구 경로도 허용하지 않는다. `recover_revoked_links.sql`을 DB 소유자가 실행해야 한다. 여행 내용은 보존한다.
5. 재발급할 새 난수 키는 요청 전에 세션 저장소에 보관한다. 응답 손실 후 동일 요청을 재시도하거나 새로고침해도 이미 발급된 키를 복구할 수 있다. 이를 보관할 수 없는 브라우저에서는 재발급을 시작하지 않는다.
6. 여행 목록은 기본적으로 편집 키를 영구 저장하지 않는다. 사용자가 선택한 여행만 계속 보관한다. 이 설정이 브라우저 방문 기록·북마크에 저장된 링크까지 삭제하지는 않는다.
7. 활성 화면에서는 약 3초 간격으로 해당 여행을 조회한다. 숨겨진 화면은 중지하고, 오류 시 최대 60초까지 간격을 늘린다. 편집 폼이 열려 있으면 입력 내용을 자동으로 덮어쓰지 않는다.
8. 홈페이지 접속만으로 방이 생성되지 않는다. ‘새 여행 만들기’를 눌러 시작한다.

## 입력 제한

기존 행을 일괄 수정하거나 삭제하지 않는다. 새 저장 요청에 다음 제한을 적용한다.

- 여행 상태의 JSON 표현 합계 2MiB, 친구 100명, 지출 5,000개, 지출당 품목 200개, 구조 깊이 12단계.
- 여행명 80자, 친구 이름 40자, 은행명 30자, 계좌 80자, 지출명 70자, 메모 140자, 카테고리 20자.
- 지출 금액은 양의 정수이며 건당 최대 1조 원. 품목 수량은 양수·최대 100만, 지원 통화와 양의 환율만 허용한다.
- 결제자·참여자·완료 송금 참여자는 같은 여행에 있어야 한다. 지출별 참여자가 중복되거나 비어 있으면 거부한다.
- 날짜는 유효한 1900~2199년 날짜, 여행·배분 기간은 최대 366일. 알려진 prototype 관련 키를 거부한다.
- CSV 파일은 2MiB, 5,000개 데이터 행, 100열까지 허용한다.

기존 기록이 제한을 초과하거나 이미 손상됐다면 저장이 거부될 수 있다. 자동으로 잘라내지 말고 소유자가 백업과 함께 검토해야 한다. 완료 송금에 등장하는 친구 삭제도 서버에서 거부된다.

## 남은 위험과 다음 결정

- **운영 반영이 최우선이다.** 파일 수정만으로 공개 기록의 편집 키나 운영 DB 접근은 폐기되지 않는다.
- 로그인 없는 기능의 특성상 유효한 링크를 가진 사람은 해당 권한을 행사한다. 전달·캡처된 링크의 실제 사용자를 구별하지 못한다. 사람별 권한 해제와 이력이 필요하면 로그인·여행 초대 방식이 적합하다.
- 익명 방 생성 RPC에는 아직 사용자/IP별 생성 제한이나 CAPTCHA가 없다. 저장 크기 제한과 자동 생성 제거는 남용 방지의 일부일 뿐이다. 운영 트래픽에 따라 서버 측 제한을 추가해야 한다. 대량 생성·부하 공격은 실행하지 않았다.
- GitHub Pages의 동일 출처 아래 다른 프로젝트도 같은 브라우저 저장 영역에 접근할 수 있다. 독립 도메인으로 출처를 분리하는 것이 다음 보완 후보다.
- 정적 HTML의 콘텐츠 보안 정책은 인라인 스크립트와 외부 실행 코드를 제한한다. 동적 스타일을 위해 인라인 CSS는 허용한다. 클릭재킹용 `frame-ancestors`는 HTML meta로 적용할 수 없어, 응답 헤더를 제어할 수 있는 호스팅·프록시가 필요하다.
- `anon` 공개 키 노출 자체는 취약점이 아니다. 검사한 JWT는 `anon` 역할이었다. 검색한 Git 기록에서 고권한 JWT와 개인키 PEM은 발견하지 않았으나, 정규식 기반 점검이 모든 비밀값을 찾아낸다는 의미는 아니다.
- 과거 Git 기록은 재작성하지 않았다. 알려진 키의 무효화가 선행되어야 하며, 기록 삭제만으로 이미 복제된 키를 회수할 수 없다.

## 2026-09-30 기능 추가

관리자 화면에만 고정 버전 Supabase SDK 2.117.2를 자체 호스팅해 Google 인증을 추가했다. 일반 여행 화면은 기존 RPC 모듈을 유지한다. 관리자별 서버 허용 목록을 사용하며 익명 전체 조회 권한은 열지 않았다. CSV 양식·예시·작성 안내도 추가했다. 상세 검증과 운영 미적용 항목은 `ADMIN_CSV_REPORT.ko.md`, 설정은 `ADMIN_SETUP.ko.md`를 따른다.
